## What survived, and is now T2's foundation

The rung was cut; its infrastructure wasn't. T2 consumes all of this **unchanged**:

| File | Why it outlived the rung |
|---|---|
| `T0_Sky/CloudField.cs` | Bake + readback + `At(x,y)`. Contains no noise. Not a MonoBehaviour precisely so T2 could reuse it — and it did, exactly as predicted. |
| `T0_Sky/CloudFieldBake.shader` | Evaluates *the* field into an RFloat RT. This **is** the weather map `_VFX.md` promised T2 and T3. |
| `T0_Sky/CloudField.hlsl` | Cloud globals + `CloudField2D()` — the basis dispatch, existing exactly once. |
| `T0_Sky/SkyRamp.hlsl` | LUT globals + row defines + `SampleRamp`. Extracted here when T0.5 became the second consumer. |
| `CloudExtrude.WindWorldOffset` | The `-wind/scale` conversion. Made `static` on 2026-07-15 so T2 shares it rather than copying the arithmetic. |

**That is the lesson this rung actually taught, and it's worth more than the mesh was.** "One field,
many consumers" and "build the spine, then hang things off it" meant a cancelled tier cost almost
nothing — the parts that mattered were never owned by it. A T0.5 that had built its own noise, its
own weather map and its own idea of cloud colour would have taken all of it to the grave, and T2
would have started from zero.

## Unverified, and never will be

`T0_Sky/CloudExtrude.cs` and `T0_Sky/T0_CloudGeo.shader` are the parts nothing else uses. They are
believed to work and are not known to. **The regression risk they carry is real and still live:**
`T0_Sky.shader` was refactored onto the two new includes as part of this rung, and that refactor was
never looked at either. If T0's sky ever looks wrong, this is the change that touched it.

## The two-implementations problem — RESOLVED 2026-07-15

The field lives in HLSL. Mesh building happens on the CPU. The same noise had to exist in two
languages, or it isn't the same field and the rung's premise collapses.

→ **Bake to a `RenderTexture`, read it back.** The C# side contains no noise at all; it asks the GPU
to evaluate the same `CloudField2D()` the sky calls, under the same global keyword. Nothing to keep
in sync, because there is nothing duplicated.

The argument that settled it wasn't the drift risk — it was that `_VFX.md` **already specified a
weather map** for T2 (spawn density) and T3 (coverage). This bake *is* that weather map. Rejected: a
C# port (two implementations, silent drift, and it makes the field-vs-placement comparison a lie),
and a compute shader (right answer only if the field rebuilds per-frame — it doesn't).

Cost accepted: a synchronous GPU readback, which stalls. Affordable only because baking is rare.

## Two decisions worth not re-deriving

Both promoted to `_VFX.md` and both now inherited by T2:

**Wind moves the frame, not the field.** The bake excludes `_CloudWindOffset` on purpose. Wind
changes every time `TimeOfDay` moves, so folding it in would re-bake *and* re-mesh every frame of a
scrub. The field is baked in its own static space and the **transform** moves: `offset = -wind/scale`.
Static field, moving frame — how Minecraft's clouds work too.

**Two keys, not one.** The *field* key (scale/octaves/lacunarity/gain/erode/basis/resolution/extent)
triggers a re-bake. The *mesh* key (coverage/thickness) only triggers a re-mesh. Scrubbing coverage
never pays the readback. Not a caching trick — it's *same field, different consumer* showing up as a
cache policy, and it's the reason the sync readback is affordable.

## Open questions, resolved while building

- **Two implementations?** → Bake + readback. Above.
- **Grid extent: patch or sky?** → A finite patch, centred on the world origin, walled at the edges.
  Kept as a visible limit rather than hidden, because "placement-based cannot fill a sky" is the
  thing the ladder exists to make you feel.
- **Share verts between faces?** → No. Shared verts average the normals and round the boxes off.
  Faceted is the point. 4× the verts, buys the look. **T2's `BuildBox` follows this.**
